Start one reader process

watch::run takes an OS lock so two readers do not race to index the same files. It loads config, prepares OCR models, watches configured folders, scans existing images, and queues files whose path or modification time is not current in SQLite.

Input: optional fixed folders and thread count, plus saved config. Output: a live Watch state and a backlog.

Code: startup and backlog
let Some(_lock) = only_watcher()? else { return Ok(()) };
let indexer = Indexer::new(threads_now, &scripts_now)?;
let mut backlog = indexer::scan(&w.folders)
    .into_iter()
    .filter(|p| w.indexer.needs_reading(p))
    .collect::<VecDeque<PathBuf>>();
watch.rs: run and only_watcher

Turn filesystem notifications into work

The notification callback sends events to the loop. Watch::on_event handles image changes, directory arrivals and removals, renames, and requests for a full rescan. A rename can update the stored path without rerunning OCR because the pixels did not change.

Input: OS filesystem events. Output: pending paths, rename state, arrived folders, or a rescan flag.

Code: event handoff
let (tx, rx) = mpsc::channel();
let mut watcher = notify::recommended_watcher(move |event| {
    let _ = tx.send(event);
})?;
for dir in &w.folders {
    watch_folder(&mut watcher, dir);
}
watch.rs: watcher setup and Watch::on_event

Wait until a screenshot is fully written

Each changed path records the last event time. After SETTLE (400 ms) without a newer event, it is eligible for reading. If image decoding still fails within the 10-second write window, it is retried instead of recorded as unreadable.

Why: capture tools often create or rewrite image files in multiple passes.

Code: quiet period
let ready: Vec<PathBuf> = map.iter()
    .filter(|(_, t)| now.duration_since(**t) >= SETTLE)
    .map(|(p, _)| p.clone())
    .collect();
watch.rs: settled | indexer.rs: written_recently

Read new captures before old backlog

Newly settled screenshots jump ahead of the startup backlog, so a fresh capture becomes searchable while an older library is still being scanned. Existing files are processed newest first. On battery, backfill is paced; new events still wake the loop.

Output: calls to Indexer::index_file, plus progress status.

Code: fresh work has priority
let fresh = settled(&mut w.pending);
if !fresh.is_empty() {
    for path in fresh {
        if index(&mut w.indexer, &path) == Read::Again {
            w.pending.insert(path, Instant::now());
        }
    }
    continue;
}
watch.rs: run loop

Follow config changes and recover lost events

When config changes, valid new settings update watched folders, clipboard tracking, OCR scripts, and thread count. Invalid partial edits are ignored until they parse. Watcher errors and queue overflow trigger a scan of configured folders, preventing a lost notification from permanently hiding a changed screenshot.

let look = if std::mem::take(&mut w.rescan) {
    w.arrived.clear();
    w.folders.clone()
} else {
    std::mem::take(&mut w.arrived)
};
watch.rs: config reload and rescan

Check whether OCR is necessary

index_file skips cloud-only files and checks the file modification time. If the same file is already indexed, it exits early. If just its thumbnail is missing, it recreates that preview without rereading text.

Code: unchanged-file fast path
if self.index.is_current(path, mtime)? {
    let thumb = gyotaku_core::thumb_path(path)?;
    if !thumb.exists() && self.index.is_visible(path)? {
        write_thumbnail(&gyotaku_ocr::load_image(path)?, &thumb)?;
        return Ok(Outcome::Thumbnail);
    }
    return Ok(Outcome::Unchanged);
}
indexer.rs: Indexer::index_file

Decode safely and classify failures

The image loader turns the file into an RGB image. Very small images are hidden from results. A recent decode failure becomes NotYet so the watcher retries; an older invalid image is stored as hidden metadata, preventing repeat work.

Input: image path. Output: RGB pixels or a retry/hidden outcome.

indexer.rs | ocr/lib.rs: load_image

Detect rectangles before reading text

Ocr::new loads ONNX Runtime and the detector and recognizer sessions once for the reader. For each image, Ocr::read asks the detector for text regions, then sends cropped regions to recognition.

Input: RGB pixels and loaded model sessions. Output: candidate rectangles and recognized strings with confidence.

ocr/lib.rs: Ocr::new and Ocr::read | det.rs

Retry uncertain lines with enabled scripts

Optional script recognizers reread only lines that look uncertain. Their result replaces the default read only when it is more confident and contains characters from that script. Gyotaku drops low-confidence and single-character results, then normalizes rectangle coordinates to image width and height.

Code: normalize OCR boxes
rect: Rect {
    x: r.x0 as f32 / w,
    y: r.y0 as f32 / h,
    w: r.width() as f32 / w,
    h: r.height() as f32 / h,
}
ocr/lib.rs: Ocr::read | core/lib.rs: Line and Rect

Write preview and searchable rows

The indexer writes a small JPEG preview, builds a Shot with source path, mtime and dimensions, and calls Index::insert. Core replaces the prior row for that path and commits shot metadata, OCR lines, combined text, folded text, and burst information in one transaction.

Code: one database transaction
let tx = self.write()?;
delete(&tx, path)?;
// insert shot and line rows
// insert combined exact and folded OCR text
tx.commit()?;
indexer.rs | index.rs: Index::insert

Separate terms from filters

Query::parse converts input into search terms and filters such as in:, date:, before:, and after:. Terms are split into three-or-more-character terms and shorter terms because the trigram index cannot search very short text.

Input: raw query text. Output: normalized terms and typed filters.

query.rs: Query::parse

Search exact OCR text first

Core builds a parameterized SQL query against shots_fts. FTS5 trigram matching handles longer terms; short terms use an escaped LIKE check. Every term must match, filters restrict paths or timestamps, and only visible screenshots are returned newest first.

Code: exact results first
let mut hits = self.find_in(false, &long, &short,
    filters, limit)?;
index.rs: find and find_in

Use folded text only to find candidates

If exact results leave room, core searches a folded version that merges selected OCR look-alikes such as 0 and o. Folding can produce false candidates, so core checks each against the original recognized text before returning it. Near hits always follow exact hits.

Code: verify candidates against original text
if terms.iter().all(|t| reads_near(&read, t, swaps(t))) {
    hits.push(Hit { near: true, ..hit });
}
index.rs: find

Return metadata, then load line boxes as needed

Index::find returns hit metadata without line text. CLI Index::search attaches matching lines before printing. The app fetches matched lines only for visible tiles, and each line's normalized rectangle becomes a box over the result image.

index.rs: search and matching_lines | app.rs: matched_lines

Turn input into result metadata

The app reads the query input, parses it to choose a search or browse limit, then calls Index::find. It stores returned hits and thumbnail paths, clears cached matched lines, and updates its current query state.

Collapse related screenshots into bursts

Near-identical screenshots are grouped so one tile can represent several captures. The app keeps the other hits behind that tile and can reveal them when the burst is unfolded.

Big picture

Gyotaku has a reader and a search app. They are separate processes. They share data through the local index and thumbnail cache.

CLI readerOCRshared core and storagesearch interfaces

Search uses the same storage: gyotaku search and gyotaku-app send queries through crates/core to this SQLite index. The app also reads previews from the thumbnail cache.

Background work

gyotaku

Indexes configured folders, watches for new files, and provides command-line search. It can run without a display.

Interactive work

gyotaku-app

Owns the GPUI window, query input, result grid, selection, and settings. It opens the same index that the reader updates.

Indexing: from file to OCR rows

The CLI owns file discovery and indexing. OCR only sees image pixels. Core only sees screenshot metadata and recognized lines. The OCR crate runs PP-OCRv6 models through ONNX Runtime on the CPU.

Search: from keystroke to result

The CLI and app share the same search code. The app asks for result metadata first and loads matched lines only for visible tiles.

Exact matches

Find what OCR read

SQLite FTS5 uses trigram indexing, so a substring can match inside a longer word. Every query term must appear in the screenshot text. Path and date filters narrow the same search.

Near matches

Recover likely OCR mistakes

If exact results do not fill the limit, core folds common look-alikes such as 0 and o. It checks candidates against the original OCR text and puts near matches after exact matches.

How do short terms and OCR mistakes work?
  • Core sends terms of three or more characters to SQLite FTS5 with the trigram tokenizer.
  • Shorter terms use a LIKE fallback, after longer terms narrow the candidate rows.
  • Exact matches fill the result list first. Core tries folded near matches only when exact results leave room.
  • Folding narrows candidates. Core checks each one against the original OCR text to avoid false matches such as finding "email" inside "internally".
  • in:, date:, before:, and after: filters apply to both exact and near searches.

What happens inside the app?
  • Gyotaku::load_hits parses the query and calls Index::find.

  • matched_lines fetches text boxes for visible results when the query is active.
  • image decodes visible thumbnails on a background executor.

What happens in CLI search?

The CLI calls Index::search, which calls find and attaches matching lines to each hit. It prints the screenshot path, near-match marker when relevant, and matching text.

What the index stores

Core keeps search data in SQLite and thumbnails in a separate cache. It stores line boxes so the app can point to the exact text that matched.

StoreContainsWhy it exists
shotsPath, modification time, image dimensions, optional thumbnail difference hash, burst idOne row per screenshot. It also tells the reader whether OCR needs to run again.
linesText, normalized x/y/width/height, OCR score, screenshot idSupports exact line highlighting and per-screenshot text display.
shots_ftsAll OCR text for one screenshotOne full-text row per screenshot allows query terms to match across different lines.
shots_nearOCR text with selected look-alike characters foldedFinds likely OCR mistakes after exact matches have been collected.
Thumbnail cacheSmall JPEG previews named from the original pathThe result grid can scroll without decoding full screenshots on every frame.

The database uses write-ahead logging so the watcher can write while the app reads. Schema versions let core migrate stored OCR text when it can, instead of forcing a full reread. The schema lives in crates/core/src/index.rs; shared value types live in crates/core/src/lib.rs.

Why does the app ask for visible lines separately?

A broad query can match many screenshots. The app first asks for hit metadata, then reads matched lines only for visible tiles. It also decodes thumbnails on a background executor. That keeps scrolling and typing from loading every full-size image or every matched line at once.

How the app stays ready

The UI process can stay resident while its window is hidden. A later launch or platform hotkey wakes it and toggles the window.

Start

Check for a resident process

crates/app/src/main.rs asks the platform module to wake an existing app. If one answers, this new process exits.

Prepare

Load shared state

The app loads configuration, binds keys, opens the default Index, creates the GPUI view, and revives the background reader. Use --once when running from source if you want the process to exit when the window closes.

Stay ready

Hide the window, keep the process

When the window closes in resident mode, the view is kept for next time and image memory is released. A later summon reopens it.

What each crate owns

Use this map when you know the feature but not the file. The Rust workspace has four crates; the website and release files support the product but do not run inside the desktop app.

crates/core | shared rules and persistence

index.rs SQLite schema and search; query.rs terms and filters; burst.rs similar-shot grouping; config.rs settings and paths; lib.rs shared data types.

crates/ocr | image to text

det.rs finds text regions; rec.rs reads lines; models.rs downloads and locates model/runtime files; lib.rs coordinates OCR.

crates/cli | commands and background reader

main.rs dispatches commands; indexer.rs processes one image; watch.rs observes folders and settings; clipboard.rs hands copied images to the reader.

crates/app | search window

app.rs owns view state and rendering; input.rs handles query editing; grid.rs lays out result tiles; images.rs decodes thumbnails; keys.rs, theme.rs, and setup.rs handle supporting UI behavior.

site/ | product website

A separate Next.js site for product information and installation instructions. It is not part of the Rust app runtime.

packaging/ and installers

Linux packages, Windows and Linux installers, desktop integration, and release resources.

.github/workflows/

CI builds and checks supported systems. Windows UI screenshots are captured in CI.

tests/fixtures/ and docs/

Test images and the written architecture, usage, compatibility, performance, and troubleshooting guides.
